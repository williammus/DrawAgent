# 全自动科研绘图 Agent 2.0 详细分阶段重构升级计划

## 1. 计划定位

本计划基于 [项目升级概要设计.md](/D:/Projects/keyanhuitu/DrawAgent/Refactoring_Upgrading_Plan/项目升级概要设计.md) 与 [全自动科研绘图Agent_prompt提取.md](/D:/Projects/keyanhuitu/DrawAgent/Refactoring_Upgrading_Plan/全自动科研绘图Agent_prompt提取.md) 制定，目标不是对 1.0 进行局部修补，而是将当前单体式原型升级为可维护、可扩展、可验证的 2.0 工程化系统。

升级原则：

- 不在现有 `appp.py` 上继续叠加复杂度
- 采用“并行新建 2.0 骨架，逐步替换 1.0 能力”的方式推进
- 先后端核心、后前端交互、最后补齐集成治理
- 所有 Agent 输入输出优先结构化，避免继续使用松散文本串联
- 提示词、状态模型、路由规则、适配器调用全部模块化

---

## 2. 当前 1.0 现状与核心问题

结合现仓库，1.0 现状可以归纳为：

1. 当前可运行逻辑几乎全部集中在 `appp.py`，属于单文件 Streamlit 原型。
2. `core` 目录大量文件为空或未形成真实分层，尚未承担稳定职责。
3. 现有流程本质是“Prompt 串行拼接 + 模型调用”，不是 LangGraph 有状态编排。
4. 没有真正的前后端分离，没有 API 层、会话层、事件流层。
5. 没有 `GraphState`、`payload_logic`、`payload_style`、`payload_mapper` 等结构化制品库。
6. Agent 提示词虽然已提取，但尚未抽象为可维护的 Prompt 资产与版本体系。
7. 图片生成、文件处理、状态管理、错误处理均直接耦合在 UI 层。
8. 缺少测试、配置管理、日志规范、目录规范和验收基线。

因此，这次升级必须按“重建架构骨架”来做，而不是“继续修补 1.0”。

---

## 3. 目标架构落地策略

### 3.1 总体实施策略

采用四条主线并行推进，但执行顺序有先后：

1. 工程骨架重建
2. 后端状态化编排重建
3. 前端单页应用重建
4. 图片生成与联调收口

### 3.2 推荐目录重组

建议逐步重构为如下结构：

```text
DrawAgent/
  legacy/
    appp.py
  backend/
    app/
      api/
      schemas/
      graph/
      agents/
      prompts/
      services/
      adapters/
      storage/
      core/
      utils/
    tests/
    requirements.txt
  frontend/
    src/
      api/
      components/
      features/
      pages/
      stores/
      hooks/
      types/
    package.json
  Refactoring_Upgrading_Plan/
```

说明：

- `legacy/` 用于冻结 1.0 原型，避免继续污染新架构。
- `backend/` 承载 FastAPI + LangGraph + 会话管理 + Agent 编排。
- `frontend/` 承载 React + TypeScript 单页对话应用。
- 提示词、数据模型、适配器、状态机必须从第一天开始独立成模块。

### 3.3 重构方法

不建议一次性推倒重写后再整体联调。推荐采用以下方法：

1. 先冻结 1.0，保留作行为参考。
2. 先把 2.0 的状态模型、目录结构、接口契约搭好。
3. 再迁移 Prompt 和 Agent 节点逻辑。
4. 再接通 LangGraph 工作流。
5. 再实现前端页面和 SSE 展示。
6. 最后接 Nano Banana2 与完整验收。

## 5. 各阶段详细计划

## Phase 0：冻结现状与建立升级基线

### 目标

在动代码之前，先明确“哪些是 1.0 遗产，哪些是 2.0 目标”，防止后续边做边改方向。

### 任务

1. 盘点当前仓库可用代码、无效代码、空文件、历史 Prompt 与 API 调用方式。
2. 标记 `appp.py` 为 1.0 原型入口，不再作为 2.0 主干继续扩写。
3. 确认 2.0 的约束边界：
   - 前后端分离
   - 无数据库
   - 单会话临时存储
   - LangChain + LangGraph
   - Nano Banana2 直出图片
4. 固化 2.0 MVP 范围：
   - 会话
   - 对话
   - 五类 Agent
   - 审查回滚
   - Prompt 确认
   - 图片生成
   - 下载

### 交付物

- 本计划文档
- 当前系统问题清单
- 2.0 MVP 范围清单

### 验收标准

- 团队对“不是修补 1.0，而是新建 2.0 主干”达成一致
- 2.0 范围不再反复摇摆

## Phase 1：搭建 2.0 工程骨架

### 目标

把项目从“单脚本原型”升级为“前后端分层工程”，先搭骨架，再填业务。

### 任务

1. 新建 `backend/` 与 `frontend/` 目录。
2. 将旧入口迁移到 `legacy/`，作为参考实现保留。
3. 初始化后端 FastAPI 项目结构。
4. 初始化前端 React + TypeScript + Vite 项目结构。
5. 建立统一配置方式：
   - `.env`
   - `settings.py`
   - 模型配置
   - 临时目录配置
6. 建立统一日志与异常处理中间件。
7. 建立开发脚本：
   - 后端启动
   - 前端启动
   - 测试
   - lint/format

### 交付物

- 新项目目录结构
- 后端基础应用可启动
- 前端空白应用可启动
- 环境配置模板

### 验收标准

- `backend` 与 `frontend` 可独立启动
- 新结构下无业务逻辑耦合在 UI 文件中

### 风险控制

- 这一阶段不接业务逻辑，避免骨架未稳先写业务

---

## Phase 2：建立后端核心契约与临时存储体系

### 目标

先把 2.0 的“状态、数据模型、会话与制品库”定下来，这是整个 LangGraph 编排的基础。

### 任务

1. 定义 Pydantic 数据模型：
   - `LogicSpec`
   - `StyleSpec`
   - `MapperSpec`
   - `ReviewSpec`
   - `FinalPromptSpec`
   - `SessionStateSummary`
2. 定义 `GraphState`。
3. 实现会话存储：
   - 内存 `SESSION_STORE`
   - 临时文件目录管理
   - TTL 清理机制
4. 定义 API DTO：
   - session init/delete
   - chat request/response
   - artifact response
   - generate response
5. 定义事件模型：
   - `stage_started`
   - `stage_completed`
   - `clarification_required`
   - `review_failed`
   - `prompt_ready`
   - `image_generated`
   - `error`
6. 建立统一错误分类：
   - 输入错误
   - 模型返回结构错误
   - 审查失败
   - 适配器错误

### 交付物

- 后端 schema 模块
- GraphState 定义
- 临时会话管理器
- 事件模型定义

### 验收标准

- 所有节点都可以围绕统一状态模型读写
- `payload_*` 与 `messages` 明确分离
- 会话销毁后，内存态和临时文件可清理

### 风险控制

- 不允许节点直接返回随意文本替代结构化对象
- 这一阶段先不追求“模型效果”，只追求“契约稳定”

---

## Phase 3：Prompt 资产化与 Agent 节点实现

### 目标

把现有 Prompt 从零散字符串升级为可维护的 Prompt 资产，并为每个 Agent 建立独立节点实现。

### 任务

1. 将已提取 Prompt 迁移到 `backend/app/prompts/`。
2. 建立 Prompt 管理规范：
   - 按 Agent 分文件
   - 支持版本号
   - 支持模板变量
   - 支持后续 A/B Prompt 替换
3. 选定逻辑拆解 Prompt 方案：
   - 默认采用 JSON 方案二
4. 为以下节点建立独立执行器：
   - `orchestrator`
   - `logician`
   - `style_configurator`
   - `visual_mapper`
   - `critic`
   - `summary`
5. 为每个节点实现：
   - 输入装配
   - LLM 调用
   - JSON 解析
   - Pydantic 校验
   - 失败重试
6. 提炼通用 LLM Client：
   - 文本模型调用
   - 超时控制
   - 结构化解析
   - 错误封装
7. 建立本地风格知识包接口，先使用静态文件或内存字典实现轻量检索。

### 交付物

- Prompt 资产目录
- 六类 Agent 节点实现
- 统一 LLM 客户端
- 风格知识包初版

### 验收标准

- 任一 Agent 可以脱离前端单独调用并返回合法结构
- Prompt 修改不需要进入业务逻辑代码内部
- 节点失败能准确报错到具体 stage

### 风险控制

- Prompt 文本和代码逻辑必须分离
- 不允许在 Orchestrator 中重新塞回“直接做全部工作”的旧单体逻辑

---

## Phase 4：实现 LangGraph 工作流与回滚机制

### 目标

把“Prompt 串行调用”真正升级为“可回滚、可澄清、可分支的状态图编排”。

### 任务

1. 实现 `InputGuard` 节点。
2. 实现 `Orchestrator` 决策节点：
   - 新建任务
   - 修改逻辑
   - 修改风格
   - 修改排版
   - 需要澄清
3. 实现新建任务主流程：
   - `Logician || Style Configurator`
   - `Visual Mapper`
   - `Critic`
   - `Summary`
4. 实现修改任务分支流程。
5. 实现 `AskClarification -> WAIT_USER` 中断机制。
6. 实现 `Critic` 失败后的定向回滚：
   - 回滚到 `logician`
   - 回滚到 `style`
   - 回滚到 `mapper`
7. 实现 `error_count` 熔断策略。
8. 为工作流提供可观测的阶段事件输出。

### 交付物

- LangGraph 工作流定义
- 路由与回滚规则
- 图状态测试样例

### 验收标准

- 新建任务链路可完整跑通到 `payload_final`
- 用户反馈可触发局部重跑，而不是全量重跑
- 澄清场景可以中断并等待用户回复

### 风险控制

- 这一阶段先做到“链路正确”，不先追求 UI 效果
- 回滚逻辑必须基于 `payload_review.error_stage`，不能写死

---

## Phase 5：实现 FastAPI 接口层与外部适配器

### 目标

把后端从“内部可运行工作流”升级为“前端可消费服务”。

### 任务

1. 实现会话接口：
   - `POST /api/session/init`
   - `DELETE /api/session/{session_id}`
2. 实现对话接口：
   - `POST /api/chat/message`
   - `GET /api/chat/stream/{session_id}`
3. 实现文件接口：
   - `POST /api/upload`
   - `DELETE /api/upload/{session_id}/{file_id}`
4. 实现制品接口：
   - `GET /api/artifacts/{session_id}`
5. 实现图片生成接口：
   - `POST /api/generate/{session_id}`
   - `GET /api/download/{session_id}`
6. 实现 Nano Banana2 适配器：
   - prompt 输入
   - 状态返回
   - 临时图片文件保存
   - 下载路径生成
7. 实现 SSE 事件推送。

### 交付物

- 完整后端 API
- Nano Banana2 适配器
- SSE 事件流

### 验收标准

- 前端不必感知内部节点实现细节，只依赖 API 契约
- 图片生成与下载链路可独立测试
- SSE 可展示阶段进度而不是轮询堆叠

### 风险控制

- 图片生成适配器必须与 Agent 节点解耦
- API 层不直接写 Prompt，不直接处理节点内部逻辑

---

## Phase 6：重建前端单页应用

### 目标

基于新的 API 和事件流，重建真正的前端界面，替代 1.0 的 Streamlit 页面。

### 任务

1. 初始化页面骨架：
   - 左侧对话区
   - 右侧结果区
   - 底部输入区
   - 操作区
2. 建立前端状态管理：
   - 当前会话
   - 对话消息
   - 工程阶段状态
   - payload 摘要
   - 最终 prompt
   - 图片结果
3. 接入 SSE，展示阶段状态：
   - 正在理解需求
   - 正在提取逻辑
   - 正在配置风格
   - 正在规划布局
   - 正在审查
   - 正在生成 Prompt
   - 正在生成图片
4. 实现文件上传交互。
5. 实现最终 Prompt 预览和“确认生成”。
6. 实现“继续反馈”进入修改工作流。
7. 实现图片预览与下载。
8. 实现“重新开始”与会话销毁。

### 交付物

- React 前端 MVP
- 对话式交互页面
- 结果展示面板

### 验收标准

- 用户能完整完成“输入 -> 生成 Prompt -> 确认 -> 出图 -> 下载”
- 用户能基于已有结果继续反馈修改
- 页面关闭后会话可销毁

### 风险控制

- 前端只负责展示与交互，不复制后端业务规则
- 任何阶段状态都以 SSE 事件为准，不在前端硬编码流程判断

## Phase 8：增强能力迭代

### 目标

在 MVP 稳定后，再逐步补强解析能力、效果质量与交互精细度。

### 可选增强项

1. PDF / Markdown / 代码仓库解析增强
2. 学科风格包扩展
3. Prompt 版本对比
4. 多候选图片生成
5. 图片质量评分与自动重生成
6. 更细粒度的用户反馈路由
7. 局部区域修改能力

### 原则

- 所有增强项都不能破坏 MVP 主链路稳定性
- 优先扩展知识包和节点能力，不优先堆前端花活

---

## 6. 关键实施顺序

为了降低返工，建议严格遵循以下顺序：

1. 先做 Phase 0-2，拿稳状态模型和接口契约。
2. 再做 Phase 3-4，把 Agent 能力和图编排跑通。
3. 再做 Phase 5，开放服务接口和 SSE。
4. 再做 Phase 6，建设前端页面。
5. 最后做 Phase 7，集中联调验收。

不建议的顺序：

1. 不要先做前端再倒逼后端设计。
2. 不要先接图片生成再定义 `payload_final`。
3. 不要继续在 `appp.py` 上补 Feature。
4. 不要在没有 schema 的前提下直接写 LangGraph。

---

## 7. 每阶段完成定义

为了防止阶段名义完成、实际返工，建议采用统一 DoD。

每个阶段必须同时满足：

1. 代码已进入目标目录结构。
2. 核心模块已有最小测试或最小可验证脚本。
3. 配置方式明确，不依赖硬编码私钥。
4. 输入输出契约有文档或 schema。
5. 失败路径有明确错误返回，而不是静默失败。

---

## 8. 建议优先级与首批落地清单

如果从现在开始立刻进入实施，建议第一批只做以下事项：

### 第一优先级

1. 新建 `backend/` 与 `frontend/` 骨架。
2. 冻结旧版 `appp.py` 到 `legacy/`。
3. 定义 `GraphState` 与五类 `payload_*` schema。

2. 先让新建任务主链路跑通到 `payload_final`。
3. 再实现 Critic 回滚与澄清中断。

### 第三优先级

1. 接通 API 和 SSE。
2. 重建前端页面。
3. 最后接 Nano Banana2 出图与下载。

## 10. 结论

这次重构升级的正确路径不是“继续把 1.0 做大”，而是：

`冻结 1.0 原型 -> 建立 2.0 工程骨架 -> 先状态模型与 Agent 编排 -> 再 API -> 再前端 -> 最后联调验收`

如果按本计划执行，2.0 可以较稳地落成一个满足概要设计要求的 MVP，并为后续风格包、解析增强和图片质量提升预留清晰扩展点。
