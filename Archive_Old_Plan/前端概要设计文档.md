# 全自动科研绘图 Agent 前端概要设计文档

## 1. 文档目的

本文档用于指导 DrawAgent 2.0 前端页面的实现，目标是让 Codex 能基于该文档直接完成首版前端工程搭建与核心页面开发。

本文档聚焦前端以下内容：

* 页面总体架构
* UI 布局与视觉风格
* 组件划分
* 状态模型
* 接口对接方式
* SSE 事件驱动逻辑
* 异常处理与边界处理
* 目录结构与实现建议

本文档不展开后端 Agent 编排、Prompt 工程、图像生成模型内部逻辑。前端只负责承接后端工作流，并将其转化为清晰、可控、接近 ChatGPT 网页版体验的对话式工作台。说明书中也明确了系统前台是“直接与用户对话的项目经理”，最终输出的是可供前端展示和驱动生成的绘图规格书。

---

## 2. 设计目标

### 2.1 核心目标

前端必须实现一个**以对话为主载体**的科研绘图工作台，让用户能够：

* 输入论文摘要、方法描述、代码逻辑、修改意见
* 看到 Agent 的思考过程与阶段反馈
* 在信息不足时回答澄清问题
* 审阅最终中英文 Prompt
* 决定“确认生成”或“继续反馈修改”
* 查看并下载最终图片

这与说明书要求完全一致。

### 2.2 体验目标

整体交互风格参考 ChatGPT 网页版，但不做品牌复制，而是遵循以下体验特征：

* 单页对话工作台
* 居中内容列
* 极简灰度主色
* 轻边框、圆角、大留白
* 输入框固定底部
* 消息流为主，辅助面板为辅
* 系统状态弱打扰、结果状态强展示

### 2.3 工程目标

前端必须满足以下工程要求：

* 以 `SSE` 为唯一主状态源，不轮询等待结果
* 支持断线重连与事件续拉
* 支持单会话下多轮修改
* 支持上传多个附件并控制本轮使用哪些附件
* 支持在 `prompt_ready` 后拉取 `payload_final`
* 支持在 `image_generated` 后通过 `/api/download/{session_id}` 展示图片
* 支持会话 TTL 过期后的可恢复提示

这些都来自接口文档的真实约束。

## 4. 总体架构设计

## 4.1 总体形态

前端采用**单页式聊天工作台**架构，整体布局建议为三栏，但默认只强调中间主聊天区：

* 左侧：轻量侧栏
* 中间：主聊天区
* 右侧：可折叠“过程 / 产物”面板

其中，中间聊天区是绝对主角；左右两侧都是辅助。

## 4.2 页面信息架构

### 左侧侧栏

用于承载弱信息，不打断主流程，建议包含：

* 产品 Logo / 名称
* “新建任务”按钮
* 当前会话状态摘要
* 已上传附件列表
* 可选的本地最近会话记录（仅 localStorage，不依赖后端）

说明：由于后端没有“获取会话详情”与“获取已上传文件列表”独立接口，侧栏中的当前附件列表必须由前端基于上传响应自行维护。

### 中间主聊天区

用于承载完整任务流，包含：

* 顶部状态条
* 欢迎区 / 空态区
* 消息流
* 最终 Prompt 卡片
* 图片结果卡片
* 底部输入区 / 操作区

### 右侧过程面板

用于展示中间产物，不抢主视线，建议默认为折叠状态。展开后包含：

* 逻辑产物 `payload_logic`
* 风格产物 `payload_style`
* 布局产物 `payload_mapper`
* 评审产物 `payload_review`
* 最终产物 `payload_final`

接口文档说明这些字段都可能为 `null`，因此该面板必须支持渐进式展示。

## 5. 页面视觉设计原则

## 5.1 整体视觉方向

整体风格参考 ChatGPT 网页版，建议采用“中性、专业、干净”的视觉语言：

* 背景：深灰或浅灰纯色背景
* 主内容区：较窄阅读列，避免横向铺满
* 卡片：低对比边框 + 轻微阴影
* 字体：系统无衬线字体栈
* 按钮：大圆角、低装饰
* 动画：只在状态变化时使用轻微淡入/骨架动画

## 5.2 主题方案

建议实现双色主题，但首版默认深色主题。

### 深色主题建议

* 页面底色：`#212121`
* 主区域底色：`#2A2A2A`
* 次级边框：`#3A3A3A`
* 主文字：`#ECECEC`
* 次文字：`#AFAFAF`
* 强调色：`#10A37F` 风格的绿色，但使用自定义值即可
* 错误色：偏柔和红色，避免刺眼

### 浅色主题建议

* 页面底色：`#F7F7F8`
* 主区域底色：`#FFFFFF`
* 边框：`#E5E7EB`
* 主文字：`#111827`
* 次文字：`#6B7280`

## 5.3 布局参数建议

* 页面最小宽度：`1280px` 优化最佳
* 主聊天列宽：`840px ~ 920px`
* 消息最大宽度：`760px`
* 输入框最大宽度：与主聊天列一致
* 卡片圆角：`16px`
* 气泡圆角：`18px`
* 顶部状态条高度：`56px`
* 底部输入区高度：`88px ~ 120px`

职责：

## 7.2 聊天流组件

### `MessageList`

职责：

* 渲染全部消息
* 自动滚动到底部
* 支持消息插入而非整列表重刷
* 支持区分消息类型

### `MessageBubble`

支持以下类型：

* `user`
* `assistant`
* `thinking`
* `clarification`
* `stage_status`
* `review_failed`
* `error`
* `final_prompt`
* `image_result`

### `ThinkingBubble`

用于显示“正在思考 / 正在处理”的特殊气泡。说明书已明确要求必须使用不同于普通消息的气泡展示思考中状态。

### `ClarificationCard`

用于展示后端 `clarification_required` 事件中的 `clarification_question`，并提示用户继续输入。接口文档也明确指出该事件发生时前端要展示补充信息输入框，并将发送按钮语义切换为“继续流程”。

### `ReviewRollbackCard`

用于展示 `review_failed` 事件，内容包括：

* 原因 `reason`
* 错误阶段 `error_stage`
* 修复建议 `fix_suggestion`

接口文档明确建议前端可提示“评审未通过，系统正在自动回滚重试”。

### `ErrorBubble`

用于展示无法自动恢复的失败状态。说明书要求错误以“标红的特殊气泡”展示；后端也定义了统一错误响应与 `error` 事件。

## 7.3 输入与操作组件

### `Composer`

职责：

* 多行文本输入
* Enter 发送，Shift+Enter 换行
* 文件上传入口
* 发送按钮
* 发送中禁用
* 澄清态下切换按钮文案为“继续流程”

### `AttachmentTray`

职责：

* 展示当前会话已上传文件
* 勾选本轮要使用的附件
* 删除附件
* 展示上传进度与大小限制提示

接口文档说明：

* 单会话最多 10 个文件
* 单文件最大 25MB
* `attachments=[]` 并不是“不带附件”，而是默认带上当前会话所有已上传文件
* 若要精确控制本轮附件，必须显式传附件 id 数组。

### `ActionButtonGroup`

仅在 `prompt_ready` 阶段出现，包含：

* 确认生成
* 有问题，我还要反馈

说明书明确要求这两个按钮在最终指令出现后展示，并且点击“有问题，我还要反馈”后要把按钮区切回输入框。

## 9. 前端状态机设计

## 9.1 一级状态机

建议页面业务状态抽象为以下主状态：

* `bootstrapping`
* `idle`
* `uploading`
* `workflow_running`
* `waiting_clarification`
* `prompt_reviewing`
* `image_generating`
* `completed`
* `failed`

## 9.2 与后端阶段的映射关系

* `idle` → 欢迎页 / 等待输入
* `clarifying` → 输入区高亮，按钮文案改为“继续流程”
* `planning / logic_ready / style_ready / mapping_ready / reviewing` → 显示思考消息 + 顶部阶段条
* `prompt_ready` → 展示最终 Prompt 卡片 + 操作按钮
* `generating_image` → 显示“正在生成图片”状态卡
* `completed` → 图片结果卡 + 下载按钮
* `failed` → 错误消息 + 允许重新输入

接口文档对这些阶段和事件的定义是明确的。

## 9.3 消息流驱动规则

消息流不直接等同于接口返回，而是根据事件进行转译：

* 用户发送消息 → 立即插入 `user` 消息
* 发送成功 → 插入 `thinking` 消息
* 收到 `stage_started` → 更新 thinking 文案
* 收到 `stage_completed` → 插入阶段完成消息
* 收到 `clarification_required` → thinking 结束，插入 `clarification` 消息
* 收到 `review_failed` → 插入 `review_failed` 消息
* 收到 `prompt_ready` → 拉取 artifacts，插入 `final_prompt` 消息
* 收到 `image_generated` → 插入 `image_result` 消息
* 收到 `error` → 插入 `error` 消息并结束运行态

## 10. 接口对接设计

## 10.1 服务层原则

前端必须拆分出独立 `api` 层，不允许在组件内直接拼接 fetch 逻辑。建议目录：

* `src/lib/http.ts`
* `src/lib/sse.ts`
* `src/api/session.ts`
* `src/api/upload.ts`
* `src/api/chat.ts`
* `src/api/artifacts.ts`
* `src/api/generate.ts`

## 10.2 启动流程

### 页面首次进入

1. 调用 `POST /api/session/init`
2. 保存 `session_id`
3. 保存 `summary`
4. 立即建立 `/api/chat/stream/{session_id}` 的 SSE 连接

接口文档也将此作为推荐首步流程。

### 上传文件

1. 调用 `POST /api/upload`
2. 缓存返回的 `files`
3. 更新侧栏和 `AttachmentTray`

### 发送消息

1. 将输入内容插入消息列表
2. 调用 `POST /api/chat/message`
3. 不等待同步结果
4. 以 SSE 事件推进 UI

文档明确指出该接口只是“已接收”，真实执行进度必须通过 SSE 获取。

---

## 10.3 SSE 设计

## 10.3.1 连接方式

使用原生 `EventSource` 即可，但为支持带 header 的续传，建议封装为两种策略之一：

* MVP：原生 `EventSource` + `after_id` query 参数重连
* 增强版：自定义 fetch-stream 封装，支持 `Last-Event-ID`

接口文档已经支持 `after_id` 与 `Last-Event-ID`。

## 10.3.2 SSE 处理规则

忽略以下事件：

* `: keep-alive`
* `heartbeat`

它们不更新业务 UI。

处理以下核心事件：

### `stage_started`

* 更新 `summary.stage`
* 置 `isWorkflowRunning = true`
* 更新 thinking 文案

### `stage_completed`

* 更新 `summary.stage`
* 追加阶段完成消息

### `clarification_required`

* 置 `needs_clarification = true`
* 写入 `clarificationQuestion`
* 切换 `composerMode = "clarification"`

### `review_failed`

* 显示评审失败卡片
* 不中断会话
* 保持流程仍可能继续

### `prompt_ready`

* 调用 `GET /api/artifacts/{session_id}`
* 读取 `payload_final`
* 置 `isPromptReady = true`

### `image_generated`

* 设置 `generatedImageUrl = /api/download/{session_id}`
* 拉起图片结果展示

### `error`

* 设置 `summary.stage = "failed"`
* 停止 loading
* 展示错误消息

这些规则在接口文档中均有明确动作建议。

---

## 10.4 产物查询设计

### `GET /api/artifacts/{session_id}`

该接口用于在关键节点刷新结构化产物，触发时机建议为：

* `prompt_ready` 后必调
* 用户主动展开 Artifact Drawer 时可补调一次
* 页面刷新恢复后可调一次

其中 `payload_final.ready_for_generation` 是是否允许出图的唯一可靠开关。

---

## 10.5 出图设计

### 触发条件

必须同时满足：

* `payload_final !== null`
* `payload_final.ready_for_generation === true`
* 当前没有运行中的后台任务

这是接口文档明确给出的出图按钮启用条件。

### 出图流程

1. 用户点击“确认生成”
2. 调用 `POST /api/generate/{session_id}`
3. 将页面置为 `image_generating`
4. 等待 SSE 的 `image_generated`
5. 将 `/api/download/{session_id}` 赋给 `img.src`

### 下载逻辑

* 下载按钮直接指向 `/api/download/{session_id}`
* 支持 `<img src>` 直接预览
* 不使用 `image_path` 直接拼接资源地址

接口文档明确说明 `image_path` 不建议前端直接访问。

## 11. 交互流程设计

## 11.1 新任务流程

1. 进入页面，自动创建 session
2. 用户上传附件
3. 用户输入任务描述
4. 页面显示 thinking 气泡
5. 后端通过 SSE 推送阶段事件
6. 若需要澄清，显示澄清卡片
7. 若流程完成，展示中英文 Prompt 卡片
8. 用户点击“确认生成”
9. 页面显示生成中状态
10. 图片生成完成，展示图片与下载按钮

这与说明书中的主前端流程和接口文档中的推荐调用流程是对齐的。

## 11.2 修改反馈流程

1. 用户看到 Prompt 卡片
2. 点击“有问题，我还要反馈”
3. 按钮区切回输入区
4. 用户输入修改意见
5. 继续调用 `POST /api/chat/message`
6. 沿用原 `session_id`
7. SSE 继续驱动后续阶段

接口文档明确要求修改逻辑/风格/排版时保持原 `session_id`。

## 11.3 澄清流程

1. 收到 `clarification_required`
2. 页面高亮显示问题
3. 发送按钮文案切换为“继续流程”
4. 用户补充说明
5. 调用 `POST /api/chat/message`
6. 后端自动识别为继续工作流，而不是新任务

这与接口文档描述一致。

## 12. 文件上传设计

## 12.1 上传入口

建议提供两种入口：

* 输入区左侧“附件”按钮
* 支持拖拽上传到主聊天区

## 12.2 上传表现

上传完成后，在侧栏与输入区上方都展示“文件 chip”：

* 文件名
* 文件大小
* 是否本轮使用
* 删除按钮

## 12.3 本轮附件选择逻辑

关键规则：

* 若用户不做选择且前端传 `attachments=[]`，后端会默认带上当前会话所有文件
* 若用户只想使用部分附件，前端必须传选中的附件 id 列表

因此前端不能简单把“未选择文件”理解为“本轮不带附件”。这个点很关键。

## 13. 错误处理设计

## 13.1 错误来源

前端错误分三类：

### A. 表单级错误

* 空输入
* 文件超大小 / 超数量
* 非法附件选择

### B. 业务级错误

* `resource_conflict`
* `session_not_found`
* `session_expired`
* `image_not_ready`
* `file_not_found`

### C. 流程级错误

* SSE `error`
* 评审失败但仍可回滚
* 图片生成适配器失败
* prompt 渲染失败

这些错误码和状态码在接口文档中都有统一定义。

## 13.2 UI 呈现方式

### 普通校验错误

在输入区附近短提示即可。

### 可恢复业务错误

以红色轻量 toast + 对话中的错误卡片双重提示。

### 流程失败

在消息流中插入红色 `ErrorBubble`，标题固定为“错误报告”，与说明书要求一致。

## 13.3 特殊错误策略

### `409 resource_conflict`

文案建议：
“当前任务仍在处理中，请等待当前流程完成后再提交新请求。”

### `410 session_expired`

文案建议：
“当前会话已过期，系统将为你重新创建新任务会话。”

处理方式：

* 弹出提示
* 自动重建 session
* 保留输入框内容
* 由用户确认后重新发送

### `404 file_not_found`

处理方式：

* 清理本地附件缓存
* 提醒用户重新上传

## 18. 核心实现策略

## 18.1 `useSessionBootstrap`

职责：

* 首次进入自动 init session
* 保存 `sessionId`
* 初始化顶部状态栏
* 启动 SSE

## 18.2 `useSSEStream`

职责：

* 维护连接状态
* 保存最新 `eventId`
* 断线重连
* 解析事件信封结构
* 分发到 store

接口文档建议缓存 `event_id`，并通过 `Last-Event-ID` 或 `after_id` 补拉。

## 18.3 `useChatWorkflow`

职责：

* 发送消息
* 插入用户消息
* 插入 thinking 消息
* 处理 composerMode 切换
* 管理确认生成 / 继续反馈

## 18.4 `useArtifacts`

职责：

* 拉取 artifacts
* 判断 `ready_for_generation`
* 把 `payload_final` 转换为 Prompt 卡片展示数据

## 20. 验收标准

前端实现完成后，至少应满足以下验收项：

1. 打开页面自动创建会话，并显示初始状态。
2. 能上传附件，且前端缓存文件 id。
3. 用户发送消息后，不靠轮询，而靠 SSE 推进状态。
4. 收到 `clarification_required` 时，页面能展示问题并继续提交流程。
5. 收到 `prompt_ready` 时，能拉取 `payload_final`，显示中英文 Prompt。
6. 页面出现“确认生成 / 有问题，我还要反馈”两个动作分支。
7. 只有在 `ready_for_generation=true` 时才能点击生成图片。
8. 收到 `image_generated` 后，能通过 `/api/download/{session_id}` 展示与下载图片。
9. 失败状态能够显示红色错误气泡，并允许再次输入。
10. 整体界面风格接近 ChatGPT 网页版：简洁、居中、对话优先、输入区固定底部。

---

## 21. 最终结论

本前端首版不应该被实现成“复杂表单页”或“多步骤 wizard”，而应该被实现成一个**ChatGPT 风格的对话式科研绘图工作台**：

* 用中间聊天流承载主任务
* 用 SSE 驱动全过程状态
* 用右侧抽屉承载结构化产物
* 用 Prompt 卡片承载“确认 / 继续反馈”
* 用结果卡片承载最终图片与下载
