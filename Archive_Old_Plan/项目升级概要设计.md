# 全自动科研绘图 Agent 概要设计说明书

## 1. 文档说明

### 1.1 文档目的
本文档用于指导“全自动科研绘图 Agent”系统的概要设计与工程落地，为 Codex 提供统一、清晰、可执行的实现蓝图。

### 1.2 项目目标
构建一个面向科研论文绘图场景的全自动 Agent 系统。系统通过对话方式接收用户输入的论文摘要、方法描述、代码逻辑或补充反馈，经过多 Agent 协同分析，生成可供 **Nano Banana2** 使用的高质量英文绘图 Prompt，并调用 Nano Banana2 完成科研图片生成、预览与下载。

### 1.3 关键约束
本项目遵循以下约束：

1. **前后端分离**
2. **采用 LangChain + LangGraph 技术栈**
3. **不使用数据库**
4. **不做多用户设计**
5. **每次会话仅临时存储于内存或临时文件**
6. **页面关闭后会话数据即销毁**
7. **最终图片由 Nano Banana2 直接生成**
8. **不采用 SVG 确定性渲染引擎作为最终出图方案**

---

## 2. 设计原则

### 2.1 结构化中间态，模型化最终出图
系统虽然最终通过 Nano Banana2 直接生成图片，但中间流程仍应坚持结构化输出。原因是科研绘图对逻辑正确性要求极高，仅依赖自然语言 Prompt 难以保证节点、层级、依赖和视觉语义的稳定性。

因此系统采用：

- 前段：结构化分析与编排
- 后段：英文 Prompt 组装与模型生成图片

即：

`用户输入 -> 多 Agent 分析 -> 结构化制品库 -> 英文 Prompt -> Nano Banana2 -> 图片输出`

### 2.2 主控只负责编排，不直接做专业生产
主控 Agent 的职责应限定为：

- 理解用户意图
- 判断当前阶段
- 调度工具或子 Agent
- 根据审查结果决定是否回滚
- 向用户发起澄清或反馈结果

主控 Agent 不直接负责：

- 提取节点拓扑
- 制定色彩规范
- 计算空间布局
- 编写最终绘图细节

这一点与原始框架说明书中的“主控官 / Orchestrator”定位一致。

### 2.3 前台消息与后台制品分离
系统必须将面向大模型上下文的 `messages` 与大体量结构化中间结果 `payload_*` 分离，以避免上下文膨胀、降低 Token 消耗，并提升节点解耦能力。该设计与原始说明书中的 GraphState / Pointer Pattern / Artifacts 模式保持一致。

### 2.4 审查与总结分离
为保证职责单一，建议保留以下边界：

- **Critic Agent**：只负责审查与放行
- **Summary Agent / Prompt Builder**：只负责将通过审查的结构化结果组装为最终英文 Prompt

最终交给 Nano Banana2 的输入，应由 Summary Agent 统一生成。

## 3. 总体架构设计

## 3.1 总体架构分层

系统整体采用五层架构：

### 第一层：前端交互层
负责用户对话、文件上传、流程状态展示、Prompt 预览、图片预览与下载。

### 第二层：API 接入层
负责接收前端请求、维护会话、提供流式响应、触发 Agent 工作流、返回中间制品和最终图片结果。

### 第三层：Agent 编排层
基于 LangGraph 构建有状态工作流，负责：

- 意图识别
- 条件路由
- 并行节点调度
- 回滚重试
- 人机澄清
- 审查放行
- Prompt 汇总

### 第四层：工具与能力层
负责：

- 文本解析
- 逻辑结构抽取
- 风格配置
- 可视化映射
- 结果审查
- Prompt 组装
- 调用 Nano Banana2 生成图片

### 第五层：临时会话存储层
负责单会话的临时状态存储，包括：

- 消息上下文
- 中间结构化 JSON
- 上传文件临时副本
- 生成图像临时文件

该层仅驻留内存或临时目录，不持久化。

## 4. 技术栈选型

## 4.1 后端技术栈
推荐采用以下后端方案：

- **Python 3.11+**
- **FastAPI**
- **LangChain**
- **LangGraph**
- **Pydantic v2**
- **Uvicorn**
- **httpx**
- **orjson**
- **asyncio**
- **python-multipart**

### 选型理由
1. LangGraph 非常适合多阶段、有状态、可回滚的 Agent 编排
2. Python 生态更适合 LLM、Prompt、结构化输出与工具链集成
3. FastAPI 适合构建流式 API、上传接口和轻量临时服务
4. Pydantic 便于严格定义各 Agent 的输入输出结构

## 4.2 前端技术栈
推荐采用以下前端方案：

- **React 18**
- **TypeScript**
- **Vite**
- **TailwindCSS**
- **shadcn/ui**
- **Zustand**
- **TanStack Query**
- **SSE（优先）**

### 选型理由
1. 前端为典型单页对话应用，无需 SSR
2. React + Vite 足够轻量，开发效率高
3. SSE 更适合展示 Agent 各阶段流式状态
4. Zustand 适合管理单会话临时状态

## 4.3 模型与服务接入
系统涉及两类模型能力：

### 文本理解与 Agent 调度模型
用于：

- 意图识别
- 逻辑提取
- 风格配置
- 视觉映射
- 审查
- Prompt 汇总

### 图像生成模型
用于最终图片生成：

- **Nano Banana2**

说明：
- Summary Agent 输出的英文 Prompt 将直接作为 Nano Banana2 的输入
- 最终科研图由 Nano Banana2 生成，不再由后端渲染引擎绘制

## 5. 核心工作流设计

## 5.1 新建绘图任务流程
针对全新绘图任务，系统工作流如下：

1. 用户输入论文摘要、方法说明、代码片段或其他科研内容
2. 主控 Agent 判断是否信息充分
3. 若信息不足，则触发澄清节点
4. 若信息充分，则并行调用：
   - Logician Agent
   - Style Configurator Agent
5. 待两个节点完成后，调用 Visual Mapper Agent
6. Visual Mapper 输出布局与空间映射描述
7. 调用 Critic Agent 进行一致性与合规审查
8. 若审查失败，则回滚至对应节点重新生成
9. 若审查通过，则调用 Summary Agent
10. Summary Agent 组装最终英文 Prompt
11. 前端展示中英文结果与确认按钮
12. 用户点击确认后，调用 Nano Banana2 生成最终图片
13. 前端展示图片，并提供下载按钮

该流程与原始文档提出的“逻辑与风格并行 -> 映射 -> 审查 -> 最终交付”的工作流一致。

## 5.2 修改任务流程
针对用户反馈的局部修改，系统支持按需回滚：

### 情况一：修改逻辑
例如：
- 缺少某个模块
- 箭头关系有误
- 某个阶段顺序不对

流程：
`Orchestrator -> Logician -> Visual Mapper -> Critic -> Summary Agent`

### 情况二：修改风格
例如：
- 颜色需要更学术
- 风格要更接近 CVPR / Nature
- 线条粗细或构图风格需要调整

流程：
`Orchestrator -> Style Configurator -> Visual Mapper -> Critic -> Summary Agent`

### 情况三：修改排版
例如：
- 主模块放中间
- 改成从左到右
- 结构更紧凑

流程：
`Orchestrator -> Visual Mapper -> Critic -> Summary Agent`

### 情况四：同时修改逻辑与风格
流程：
`Orchestrator -> Logician + Style Configurator -> Visual Mapper -> Critic -> Summary Agent`

## 5.3 澄清流程
若用户输入不完整，主控 Agent 必须优先发起澄清，而不是带着假设继续执行。

典型触发场景：

- 用户只说“帮我画个图”
- 用户未说明学科或论文场景
- 用户反馈“感觉不太对”，但未说明是逻辑还是风格问题

工作流：

`Orchestrator -> AskClarification -> 等待用户回复 -> Orchestrator`

这与原始框架说明书中的“CLARIFY -> PLAN -> ACT”原则保持一致。

## 6. 多 Agent 设计

## 6.1 Orchestrator Agent（主控 Agent）

### 职责
- 作为系统唯一对客窗口
- 解析用户意图
- 判断当前处于新建任务、修改任务还是澄清阶段
- 负责任务拆解、路由和阶段推进
- 根据 Critic 报告进行重试或回滚
- 维护用户对话体验

### 输入
- 用户文本
- 历史 messages
- 错误报告
- 各 payload 的状态摘要

### 输出
- Tool Call
- 对用户的澄清话术
- 最终流程状态说明

### 说明
Orchestrator 不直接产出科研图逻辑与视觉细节，只负责编排。

---

## 6.2 Logician Agent（逻辑拆解 Agent）

### 职责
从论文摘要、方法描述、技术文本或代码逻辑中提取科研图所需的抽象逻辑结构。

### 输入
- `source_text`
- `focus_area`
- `modification_instruction`

### 输出
结构化逻辑结果 `payload_logic`，建议包括：

- 图标题
- 方法简述
- 关键模块节点
- 模块依赖关系
- 数据流
- 容器结构
- 分组信息

### 输出示例字段
- `chart_title`
- `core_method_summary`
- `containers`
- `nodes`
- `edges`

---

## 6.3 Style Configurator Agent（风格配置 Agent）

### 职责
根据目标学科、期刊/会议风格和用户偏好，生成科研图的视觉规范。

### 输入
- `primary_discipline`
- `target_journal`
- `user_preferences`

### 输出
结构化风格结果 `payload_style`，建议包括：

- 主色
- 辅助色
- 字体
- 线宽
- 形状风格
- 布局偏好
- 图例规范
- 禁用项
- 风格关键词

### 说明
本项目不要求接入数据库式 RAG，可采用**本地静态风格知识包 + 内存检索**的方式实现轻量化风格库。

---

## 6.4 Visual Mapper Agent（视觉映射 Agent）

### 职责
将抽象逻辑结构映射为适合图片生成模型理解的空间描述与视觉布局描述。

### 输入
- `payload_logic`
- `payload_style`
- `layout_preferences`

### 输出
结构化映射结果 `payload_mapper`，建议包括：

- 叙事方向
- 区域划分
- 主模块相对位置
- 次模块相对位置
- 分组区域说明
- 连线方式说明
- 视觉层级说明
- 图例摆放建议

### 重要说明
由于本项目不再走 SVG 渲染路径，Visual Mapper 不需要输出绝对像素级坐标，而应优先输出：

- 相对布局
- 区域描述
- 视觉关系
- 可供 Summary Agent 组织为 Prompt 的空间信息

即该节点更偏向“视觉构图规划”，而不是“精确画布渲染”。

---

## 6.5 Critic Agent（审查 Agent）

### 职责
对前序节点结果进行严格审查，只做质检，不负责编写最终 Prompt。

### 输入
- `payload_logic`
- `payload_style`
- `payload_mapper`

### 输出
审查结果 `payload_review`，包括：

- `passed`
- `reason`
- `error_stage`
- `fix_suggestion`

### 审查范围
1. 节点是否缺失
2. 逻辑链路是否自洽
3. 风格是否与学科/期刊匹配
4. 构图是否拥挤或冲突
5. 是否存在明显不适合科研图的视觉表达
6. 是否满足 Nano Banana2 生成所需的明确性

### 输出约束
- 审查通过：输出通过报告
- 审查失败：输出失败原因与建议回滚阶段

---

## 6.6 Summary Agent（最终总结 / Prompt 生成 Agent）

### 职责
将逻辑、风格、视觉映射结果统一组装为：

1. 最终英文 Prompt
2. 中文解释版说明
3. 可供前端展示的最终摘要

### 输入
- `payload_logic`
- `payload_style`
- `payload_mapper`
- `payload_review`

### 输出
`payload_final`，建议包括：

- `final_prompt_en`
- `final_prompt_cn`
- `prompt_version`
- `generation_notes`
- `ready_for_generation`

### 关键要求
Summary Agent 输出的英文 Prompt 将直接交由 **Nano Banana2** 进行图片生成，因此它必须满足：

1. 描述完整
2. 结构清晰
3. 视觉要求明确
4. 适合科研图片生成
5. 避免泛化、模糊、艺术化过强表达
6. 突出学术图、结构图、方法图、流程图等语义

### 输出定位
Summary Agent 是系统最终的“可交付文本产物生成者”。

---

## 6.7 Image Generation Adapter（Nano Banana2 调用节点）

### 职责
接收 Summary Agent 输出的英文 Prompt，并调用 Nano Banana2 生成最终图片。

### 输入
- `final_prompt_en`

### 输出
- 图片二进制或图片 URL
- 生成状态
- 错误信息
- 临时下载路径

### 说明
该节点不是思考型 Agent，而是服务适配器节点。

## 7. LangGraph 编排设计

## 7.1 GraphState 设计

建议定义如下状态结构：

```python
from typing import TypedDict, Annotated, Optional, Any, Dict, List
from langgraph.graph.message import add_messages
from langchain_core.messages import AnyMessage

class GraphState(TypedDict):
    # 前台消息区
    messages: Annotated[List[AnyMessage], add_messages]

    # 会话信息
    session_id: str
    stage: str
    intent: str

    # 输入信息
    source_text: Optional[str]
    source_files: Optional[List[Dict[str, Any]]]
    research_context: Optional[Dict[str, Any]]
    user_feedback: Optional[str]

    # 制品库
    payload_logic: Optional[Dict[str, Any]]
    payload_style: Optional[Dict[str, Any]]
    payload_mapper: Optional[Dict[str, Any]]
    payload_review: Optional[Dict[str, Any]]
    payload_final: Optional[Dict[str, Any]]

    # 图片生成结果
    generated_image_path: Optional[str]
    generated_image_meta: Optional[Dict[str, Any]]

    # 控制字段
    error_count: int
    last_error: Optional[str]
    needs_clarification: bool
    user_confirmed: bool
````

### 设计要点

1. `messages` 只存对话与简短回执
2. 结构化重载数据存放在 `payload_*`
3. 图片生成结果单独存放
4. 错误控制字段用于熔断与重试控制

这与原始设计文档中强调的“主控看消息区，工具间通过暗室/制品库传递大体量 JSON”的思想一致。

## 7.2 状态流转建议

### 新任务流程

`START -> InputGuard -> Orchestrator -> [Logician || Style Configurator] -> Visual Mapper -> Critic -> Summary Agent -> WaitUserConfirm -> Nano Banana2 Adapter -> END`

### 修改逻辑

`Orchestrator -> Logician -> Visual Mapper -> Critic -> Summary Agent`

### 修改风格

`Orchestrator -> Style Configurator -> Visual Mapper -> Critic -> Summary Agent`

### 修改排版

`Orchestrator -> Visual Mapper -> Critic -> Summary Agent`

### 澄清中断

`Orchestrator -> AskClarification -> WAIT_USER`

* 英文 Prompt

* “继续反馈”按钮

若用户点击确认，则调用 Nano Banana2。
若用户点击继续反馈，则进入修改工作流。

## 10. API 设计

## 10.1 会话接口

### `POST /api/session/init`

创建临时会话。

返回：

* `session_id`

### `DELETE /api/session/{session_id}`

销毁临时会话及相关内存/临时文件。

---

## 10.2 对话接口

### `POST /api/chat/message`

提交用户消息并启动或推进 Agent 工作流。

请求体：

* `session_id`
* `message`
* `attachments`

返回：

* 当前阶段结果
* 或通过 SSE 推送过程事件

### `GET /api/chat/stream/{session_id}`

流式接收 Agent 过程事件。

---

## 10.3 文件接口

### `POST /api/upload`

上传论文摘要、PDF、Markdown、代码片段等临时文件。

### `DELETE /api/upload/{session_id}/{file_id}`

删除某个临时上传文件。

---

## 10.4 制品接口

### `GET /api/artifacts/{session_id}`

获取当前会话的中间结构化制品，包括：

* `payload_logic`
* `payload_style`
* `payload_mapper`
* `payload_review`
* `payload_final`

---

## 10.5 图片生成接口

### `POST /api/generate/{session_id}`

根据当前已确认的 `final_prompt_en` 调用 Nano Banana2 生成图片。

返回：

* 图片生成状态
* 图片临时地址
* 错误信息

### `GET /api/download/{session_id}`

下载最终生成的图片。

## 11. 临时存储与隐私设计

## 11.1 存储原则

本项目不使用数据库，不做持久化，不保留用户历史。

## 11.2 后端存储方案

建议采用两类临时存储：

### 1. 内存会话存储

用于保存：

* GraphState
* 中间 payload
* 会话控制信息

可使用进程内字典维护：

```python
SESSION_STORE = {
    session_id: GraphState
}
```

### 2. 临时文件目录

用于保存：

* 上传文件临时副本
* Nano Banana2 返回的图片临时文件

建议路径：

* `/tmp/research-drawing-agent/{session_id}/`

## 11.3 会话销毁策略

采用双重清理机制：

### 主动清理

* 前端页面关闭时调用 `DELETE /api/session/{session_id}`

### 被动清理

* 服务端设置 TTL，例如 30 分钟无活动自动销毁
* 服务重启时清理遗留临时目录

## 11.4 隐私要求

必须遵守以下原则：

1. 不写数据库
2. 不保留会话历史
3. 不记录原始用户全文日志
4. 不保留最终图片长期副本
5. 不做多用户身份体系
6. 不跨会话复用用户数据

## 12. 错误处理设计

## 12.1 错误分类

### 输入错误

* 内容为空
* 文件不支持
* 信息不足

### Agent 输出错误

* JSON 解析失败
* 字段缺失
* 结构不合法

### 审查失败

* 节点缺失
* 逻辑不完整
* 风格不匹配
* 构图描述冲突

### 图片生成失败

* Nano Banana2 调用失败
* 返回图片为空
* 下载文件损坏

## 12.2 错误策略

1. 单节点可重试 1~2 次
2. 使用 `error_count` 控制熔断
3. 审查失败时定向回滚至对应节点
4. 无法自动恢复时，前端展示“错误报告”气泡
